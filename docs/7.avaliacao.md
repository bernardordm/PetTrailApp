# 7. Avaliação da Arquitetura

_Esta seção descreve a avaliação da arquitetura apresentada, baseada no método ATAM._

## 7.1. Cenários

_Os cenários abaixo foram selecionados para demonstrar a satisfação dos requisitos não-funcionais mais críticos do PetTrail, cobrindo segurança, controle de acesso, integridade de dados e desacoplamento assíncrono._

**Cenário 1 - Segurança / Autenticação (RNF004):** Um usuário tenta acessar qualquer endpoint protegido da API sem apresentar um token JWT válido. O sistema deve rejeitar a requisição com status 401 (Unauthorized). Adicionalmente, ao fornecer credenciais incorretas (e-mail inexistente ou senha inválida), o serviço de autenticação deve lançar exceção antes de gerar qualquer token.

**Cenário 2 - Controle de Acesso por Perfil (RNF004 + RNF005):** Um tutor autenticado tenta consultar ou modificar um pet que pertence a outro tutor. O sistema deve identificar a divergência entre o `tutor_identifier` do recurso e o `sub` embutido no JWT e rejeitar a operação com status 403 (Forbidden), sem expor os dados do recurso alheio.

**Cenário 3 - Integridade de Dados de Usuários (RNF004 + RNF005):** Ao cadastrar um novo usuário, o sistema deve garantir que: (a) senhas nunca são armazenadas em texto puro — devem ser submetidas ao algoritmo bcrypt com fator de custo 10; (b) e-mails duplicados são rejeitados imediatamente com status 409 (Conflict), preservando a unicidade do identificador de acesso.

**Cenário 4 - Desacoplamento e Disponibilidade do Passeador (RNF007 + RNF003):** Ao ativar sua disponibilidade, o passeador deve ter seu status registrado simultaneamente no banco relacional (PostgreSQL via TypeORM) e no Firebase Realtime Database, garantindo que tutores vejam a localização em tempo real. Ao desativar, o nó de localização no Firebase deve ser removido. Falhas no Firebase não devem impedir a operação principal no banco relacional.

## 7.2. Avaliação

| **Atributo de Qualidade:** | Segurança |
| --- | --- |
| **Requisito de Qualidade** | Todos os endpoints REST devem exigir autenticação via token JWT; o tipo de perfil deve ser embutido no token para controle de acesso por perfil (RNF004) |
| **Preocupação:** | Um usuário não autenticado ou com credenciais inválidas não deve conseguir acionar nenhuma operação protegida do sistema |
| **Cenário(s):** | Cenário 1 |
| **Ambiente:** | Sistema em operação normal — backend NestJS em execução |
| **Estímulo:** | Requisição com e-mail inexistente ou senha incorreta ao endpoint de login |
| **Mecanismo:** | O `AuthService` valida as credenciais via `UserRepository.findByEmail` e comparação bcrypt. Em caso de falha em qualquer etapa, lança `UnauthorizedException` antes de acionar o `JwtService`. O token gerado carrega `{ sub: identifier, role }`, consumido por Guards em todos os endpoints protegidos |
| **Medida de Resposta:** | Nenhum token é emitido para credenciais inválidas; a exceção é lançada em 100% dos casos de e-mail inexistente e de senha incorreta, conforme verificado pelos testes unitários |

**Considerações sobre a arquitetura:**

| **Riscos:** | A estratégia stateless do JWT não permite revogar tokens antes do vencimento; um token vazado permanece válido até expirar |
| --- | --- |
| **Pontos de Sensibilidade:** | O tempo de expiração do JWT precisa ser curto o suficiente para limitar a janela de abuso em caso de vazamento |
| **Tradeoff:** | Stateless (JWT) elimina necessidade de sessão no servidor e facilita escalonamento horizontal, mas sacrifica a capacidade de revogação imediata — troca de escalabilidade por controle fino de sessão |

| **Atributo de Qualidade:** | Segurança / Isolamento de Dados |
| --- | --- |
| **Requisito de Qualidade** | O tipo de perfil embutido no token deve ser usado para controle de acesso; credenciais e dados de cada perfil devem ser isolados (RNF004 + RNF005) |
| **Preocupação:** | Um tutor autenticado não deve visualizar nem alterar pets cadastrados por outro tutor, mesmo conhecendo o identificador do recurso |
| **Cenário(s):** | Cenário 2 |
| **Ambiente:** | Sistema em operação normal — usuário tutor autenticado com JWT válido |
| **Estímulo:** | Requisição GET ou PATCH sobre um pet cujo `tutor_identifier` difere do `sub` presente no token do solicitante |
| **Mecanismo:** | O `PetsService` recupera o pet pelo `identifier` e compara o campo `tutor_identifier` com o identificador do usuário autenticado extraído do token. Divergência resulta em `ForbiddenException` antes de qualquer retorno de dados |
| **Medida de Resposta:** | 100% das tentativas de acesso cruzado resultam em status 403, sem exposição de dados alheios, conforme verificado pelos testes unitários |

**Considerações sobre a arquitetura:**

| **Riscos:** | Não identificado — a verificação ocorre na camada de serviço, independente do transporte |
| --- | --- |
| **Pontos de Sensibilidade:** | A verificação depende de o `tutor_identifier` ser gravado corretamente no momento do cadastro do pet |
| **Tradeoff:** | Verificação no serviço (em vez de no banco via RLS) mantém a lógica testável e portável, mas adiciona uma roundtrip ao banco para buscar o recurso antes de verificar a permissão |

| **Atributo de Qualidade:** | Segurança / Integridade de Dados |
| --- | --- |
| **Requisito de Qualidade** | Senhas devem ser armazenadas com hash bcrypt; e-mails duplicados devem ser rejeitados (RNF004 + RNF005) |
| **Preocupação:** | Vazamento do banco de dados não deve expor senhas em texto puro; dois usuários não devem compartilhar o mesmo e-mail |
| **Cenário(s):** | Cenário 3 |
| **Ambiente:** | Sistema em operação normal — cadastro de novo usuário |
| **Estímulo:** | Tentativa de cadastro com e-mail já existente; tentativa de cadastro com senha em texto puro |
| **Mecanismo:** | O `UsersService` consulta `UserRepository.findByEmail` antes de criar: se o e-mail existe, lança `ConflictException`. Em caso de e-mail livre, chama `bcrypt.hash` com fator de custo 10 e armazena apenas o hash. A senha original nunca é persistida |
| **Medida de Resposta:** | Conflito de e-mail rejeitado com 409 em 100% dos casos; toda senha armazenada é um hash bcrypt verificável, conforme testes unitários |

**Considerações sobre a arquitetura:**

| **Riscos:** | Não identificado para o escopo do MVP |
| --- | --- |
| **Pontos de Sensibilidade:** | O fator de custo do bcrypt (10) deve ser revisado periodicamente conforme a evolução do hardware |
| **Tradeoff:** | bcrypt é lento por design (resistência a brute force), o que aumenta levemente a latência do cadastro e do login — troca de velocidade por segurança na autenticação |

| **Atributo de Qualidade:** | Disponibilidade / Desacoplamento Assíncrono |
| --- | --- |
| **Requisito de Qualidade** | A arquitetura deve permitir escalar o microserviço de forma independente; falhas no serviço auxiliar não devem afetar a experiência principal (RNF003 + RNF007) |
| **Preocupação:** | A ativação de disponibilidade do passeador envolve dois sistemas (PostgreSQL e Firebase); a inconsistência entre eles pode fazer o passeador aparecer no mapa sem estar realmente disponível, ou vice-versa |
| **Cenário(s):** | Cenário 4 |
| **Ambiente:** | Sistema em operação normal — passeador altera disponibilidade via app mobile |
| **Estímulo:** | Passeador ativa (`available: true`) ou desativa (`available: false`) sua disponibilidade |
| **Mecanismo:** | O `WalkersService` atualiza o campo `available` e `status` no PostgreSQL via `WalkerRepository.update` e, em seguida, chama `FirebaseService.initWalkerLocation` (ativação) ou `FirebaseService.clearWalkerLocation` (desativação). O Firebase Realtime Database serve como camada de presença para rastreamento em tempo real no mapa |
| **Medida de Resposta:** | Ambas as operações (banco relacional + Firebase) são acionadas em cada mudança de disponibilidade, conforme verificado pelos testes unitários de `WalkersService` |

**Considerações sobre a arquitetura:**

| **Riscos:** | A operação no Firebase ocorre após o banco — uma falha de rede após a gravação no banco pode gerar inconsistência temporária de presença |
| --- | --- |
| **Pontos de Sensibilidade:** | A sincronização banco + Firebase não é transacional; falha parcial requer reconciliação manual ou reprocessamento |
| **Tradeoff:** | Separar persistência relacional (PostgreSQL) de presença em tempo real (Firebase) permite escalar cada um de forma independente e não bloqueia o fluxo principal em caso de lentidão do Firebase, mas introduz possibilidade de inconsistência temporária |

### Avaliação Geral da Arquitetura

**Pontos fortes:**
- A autenticação stateless via JWT permite escalonamento horizontal sem estado de sessão compartilhado entre instâncias do backend
- O isolamento de dados por perfil é verificado na camada de serviço, tornando-o portável e testável independente do banco
- O processamento assíncrono de relatórios via RabbitMQ desacopla o microserviço do fluxo crítico do passeio, evitando que falhas no worker impactem a experiência do usuário
- A separação entre persistência relacional (PostgreSQL) e presença em tempo real (Firebase) permite otimizar cada camada para seu caso de uso específico

**Limitações:**
- A ausência de revogação de tokens JWT impede o logout imediato em caso de comprometimento de credenciais
- A sincronização banco + Firebase não é atômica, podendo gerar inconsistências temporárias de presença do passeador no mapa
- Os testes cobrem a camada de serviço (unitários); testes de integração end-to-end com banco real e WebSocket ainda são necessários para validar os requisitos de latência (RNF001) e disponibilidade (RNF002) em condições de carga
