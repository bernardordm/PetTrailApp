## 3.2. Requisitos Não-Funcionais

| **ID** | **Descrição** |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RNF001 | **Latência de rastreamento:** as coordenadas GPS devem ser transmitidas e refletidas no mapa do tutor em no máximo 30 segundos após a captura, garantindo rastreamento percebido como tempo real |
| RNF002 | **Disponibilidade:** o backend e o microserviço devem operar com disponibilidade na maior parte do tempo, dado que falhas impedem passeios em andamento |
| RNF003 | **Escalabilidade:** a arquitetura de filas (RabbitMQ) deve permitir escalar horizontalmente o microserviço de processamento de relatórios sem impacto no backend principal |
| RNF004 | **Segurança:** todos os endpoints REST devem exigir autenticação via token JWT; o tipo de perfil deve ser embutido no token para controle de acesso por perfil |
| RNF005 | **Isolamento de dados:** as credenciais de banco de dados (RDS) e mensageria (Amazon MQ) devem ser fornecidas exclusivamente via variáveis de ambiente, nunca hardcoded |
| RNF006 | **Persistência confiável:** o banco de dados PostgreSQL deve ser hospedado em instância gerenciada (AWS RDS) com backups automáticos habilitados e acesso restrito à VPC privada |
| RNF007 | **Desacoplamento assíncrono:** o processamento de relatórios pós-passeio deve ser inteiramente assíncrono via fila, de modo que falhas no microserviço não afetem a experiência do passeador ao finalizar o passeio |
| RNF008 | **Operação em segundo plano:** o app mobile deve capturar localização GPS mesmo com a tela bloqueada ou o app em background, utilizando flutter_background_service |
| RNF009 | **Usabilidade multiplataforma:** o painel web deve ser responsivo e funcional nos principais navegadores desktop (Chrome, Firefox, Edge, Safari) |
| RNF010 | **Custo operacional:** a arquitetura do MVP deve ser viável dentro do crédito gratuito mensal de U$200 da Google Maps Platform e do free tier da AWS (instância db.t3.micro) |

## 3.3. Restrições Arquiteturais

As restrições impostas ao projeto que afetam sua arquitetura são:

- O app mobile deve ser desenvolvido em **Flutter (Dart)**, atendendo Android e iOS a partir de uma única base de código;
- O frontend web deve ser desenvolvido em **Next.js (React)**;
- O backend principal deve ser desenvolvido em **NestJS (Node.js/TypeScript)**;
- O microserviço de processamento assíncrono deve ser desenvolvido em **Node.js (TypeScript)**;
- A comunicação em tempo real entre clientes e backend deve utilizar **WebSocket**;
- O banco de dados relacional deve ser **PostgreSQL**;
- A mensageria entre o backend e o microserviço deve utilizar **RabbitMQ**;
- Os serviços de mapas, geração de imagem de trajeto, cálculo de rota e geocodificação devem utilizar exclusivamente as **APIs do Google Maps Platform**;
- O pagamento entre tutor e passeador é realizado **fora da plataforma** (dinheiro ou PIX), sendo vedada a integração de gateway de pagamento no escopo atual;
- Cada passeio deve envolver **apenas 1 pet por vez**, sem suporte a passeios coletivos;
- Os passeios são sempre **imediatos**, sem suporte a agendamento futuro.

## 3.4. Mecanismos Arquiteturais

*Visão geral dos mecanismos que compõem a arquitetura do software baseando-se em três estados: (1) análise, (2) design e (3) implementação. Em termos de Análise devem ser listados os aspectos gerais que compõem a arquitetura do software como: persistência, integração com sistemas legados, geração de logs do sistema, ambiente de front end, tratamento de exceções, formato dos testes, formato de distribuição/implantação (deploy), entre outros. Em Design deve-se identificar o padrão tecnológico a seguir para cada mecanismo identificado na análise. Em Implementação, deve-se identificar o produto a ser utilizado na solução.*

*Ex: Análise (Persistência), Design (ORM), Implementação (Hibernate).*

| **Análise** | **Design** | **Implementação** |
| ---------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------ |
| Persistência | ORM relacional com mapeamento de entidades | TypeORM + PostgreSQL (AWS RDS) |
| Front end web | SPA com renderização híbrida e roteamento por perfil | Next.js (React) hospedado no Render |
| Front end mobile | Aplicação cross-platform com UI nativa | Flutter (Dart) |
| Back end | API RESTful + servidor WebSocket unificado | NestJS (Node.js/TypeScript) hospedado no Render |
| Processamento assíncrono | Worker de fila com consumo contínuo | Microserviço Node.js (Render Background Worker) |
| Comunicação em tempo real | WebSocket publish/subscribe | NestJS WebSocket Gateway (Socket.IO ou ws nativo) |
| Registro de coordenadas GPS | Banco em tempo real com sincronização e listeners | Firebase Realtime Database (`firebase_database` no Flutter; `firebase-admin` no NestJS) |
| Mensageria | Fila de mensagens com filas dedicadas por domínio | RabbitMQ (AWS Amazon MQ — Single-instance) |
| Geolocalização mobile | Captura GPS em foreground e background | geolocator + flutter_background_service |
| Mapas e rastreamento mobile | SDK nativo de mapas com renderização de polilinhas | Google Maps Flutter SDK |
| Mapas no painel web | Renderização de mapa interativo no browser | Google Maps JavaScript API |
| Geração de imagem de trajeto | Chamada HTTP a API de mapas estáticos | Google Static Maps API |
| Cálculo de rota e ETA | Requisição REST à API de direções | Google Directions API |
| Geocodificação | Conversão endereço → coordenadas no cadastro | Google Geocoding API |
| Envio de e-mail | SMTP ou API transacional | Nodemailer / SendGrid |
| Autenticação | Autenticação stateless com token assinado | JWT (JSON Web Token) via NestJS Guards |
| Log do sistema | Registro estruturado de eventos e erros | Logger nativo do NestJS / Winston |
| Teste de software | Testes unitários e de integração | Jest (backend NestJS e microserviço) + Flutter Test (mobile) |
| Configuração de ambiente | Variáveis de ambiente para segredos e configurações | `.env` + variáveis de ambiente no Render e AWS |
